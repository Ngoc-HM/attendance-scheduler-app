## Objective weights (engine)
`Minimize( slack·10000 + compDaySlack·2000 + individualADGap·300 + balanceAD·100 + premiumOff·30 + offPairing·15 )`
— `slack_registry.SLACK_WEIGHT`, `constraints_comp_days.COMP_WEIGHT` and
`objectives.WEIGHTS`. Rule slack (off days, rolling rest, consecutive working,
off-chain, staffing, pure-A days) dwarfs everything; comp-day shortfall/excess
slack sits below staffing (a CD yields to flight cover) but above every
objective. `offPairing` rewards adjacent weekly offs with no weekend bias
(#16). When ordinary A/Duty staffing is insufficient, the generated roster
reports a violation instead of creating an A/D double shift.

Since 2026-11-08 the solve runs in two phases (#45): phase 1 minimises
`slack·10000 + compDaySlack·2000` alone; phase 2 minimises the full
expression above with that slack total as an upper bound. The weights are
unchanged.

## Migration strategy
Alembic is authoritative; head is **`0009`**: `0001` baseline, `0002`
`carry_premium_off` + `shift_change_requests`, `0003` A1–A4 collapsed into A +
`users.code` + `role_code_counters`, `0004` `flight_presets`, `0005` role F,
`0006` `time_clock_entries`, `0007` `self_arrange_requests`, `0008`
`annual_leave_quota` (drops `annual_leave_balance`), `0009` unique
(`day`, `flt_number`) on `flights` after removing duplicates (lowest id kept,
#49). Run `alembic upgrade head` **before** starting the backend on an
existing database.

`create_all` (`AUTO_CREATE_TABLES`, dev only) is kept ONLY for a brand-new
database and never ALTERs existing tables; once the database has an
`alembic_version` table it is skipped with a warning (#55). A database that
`create_all` built (no `alembic_version`) already holds the schema of the code
that created it: stamp the revision that was head in that code — `alembic
stamp head` when it was the current code — then `alembic upgrade head`.
Stamping `0001` on such a database is wrong: `0002`+ would try to create
tables that exist (DuplicateTable).
